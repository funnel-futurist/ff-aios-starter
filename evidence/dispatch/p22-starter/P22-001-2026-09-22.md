## 2. The outcome: a proven installation path

`approved pinned package -> role-scoped /start -> config and credential references -> verification
-> upgrade and rollback that preserve state.`

Implemented in `scripts/aios/` (Python 3.9, standard library only, so a client machine needs no
`pip install`), with the state boundary as the load-bearing idea:

- **managed** files belong to the release: replaced on upgrade, restored on rollback, re-hashed on
  every verify.
- **seed** files are written once if absent and then never touched again - `CLAUDE.md`, the
  foundations, the logs, the deliverables.
- anything the operator creates is not in the manifest, so no operation can see or delete it.

Every operation is verified by **readback**: re-hashing what is on disk and comparing it to the
manifest. The installer reporting success is not evidence, and the verifier is proven able to
fail (a hand edit is caught, exit 6; an interrupted upgrade is caught, exit 5).

## 3. The governance defect, through all five closeout steps

**Finding.** `.github/CODEOWNERS` shipped with literal `[REPO_OWNER]`, `[PRIMARY_REVIEWER]` and
`[TECHNICAL_REVIEWER]` owner tokens. GitHub treats an unparseable owner as no owner, so nine rules
covering migrations, `.env*`, `.github/`, `CLAUDE.md` and the skills/hooks engine matched nobody.

**Classify.** Systemic, and worse than a single dead gate: this is a *template*. Every repository
generated from it inherits the file, so the defect reproduces into every client workspace. The
repo's own drift detector checked only that the file existed.

**Canonicalize.** Three checks, because the file lies in three distinct ways - unresolved
placeholders, owners that are not `@user` / `@org/team` / email, and a missing repository binding.
That last one is the template trap: a generated repo inherits the publisher's owners, who have no
access there, so the rules again match nobody. Rendered files now carry
`# aios-codeowners-for: <owner>/<repo>`, and a mismatch is an error instead of a silent downgrade.
The placeholder template moved to `templates/governance/CODEOWNERS.template`, where placeholders
belong, and `governance render` refuses to emit a rule whose owners are all unfilled.

**Test.** `governance check` fails on the real file (exit 8); `verify-branch-protection.sh` now
fails instead of ticking it, and additionally detects an unprotected branch **without** an admin
token via `branches/main .protected` - previously a non-admin run reported INCONCLUSIVE on the
loudest possible finding. A CI job runs the check on every push.

**Propagate.** 32 repositories swept across the three owners in the portfolio (`gh api` per repo,
default branch resolved rather than assuming `main`):

- **1** carries the `[PLACEHOLDER]` defect: this one. It has not yet reached another repo in the
  portfolio. Client repos generated from the template are in clients' own accounts and are not
  visible from here, so this is a bound, not a clean bill of health.
- **6** have a CODEOWNERS file at all; **3 of 32** have branch protection on their default branch.
- Therefore **5 repositories have a filled CODEOWNERS that enforces nothing**, for the same reason
  this one would after the placeholders are fixed. That is the generalised finding: the
  portfolio's code-owner rules are mostly decorative, and the missing piece is branch protection,
  which needs an admin.

## 5. Sanitization, and what it does not prove

Release-mode sanitization scans exactly the file set a release ships. The client-name denylist is
**supplied at run time and never committed** - in a public repo, a file listing every client name
would be the leak it is meant to prevent.

**Real package, 282 files: 1 finding.** A live `docs.google.com` document URL in a client-facing
skill.

Identified and measured under founder correction `97f2671` item 5, which reclassified this from a
decision Phoenix was being asked to make blind into an identification question. Both halves
verified here independently rather than taken on report:

- **Reachable:** an anonymous, unauthenticated export returns **HTTP 200 and the full 45,328
  bytes**. Anyone with the link reads the whole document.
- **Not sensitive:** my own scanner over that exported text, using the real client roster as the
  denylist and a second pass including the two client names that are ordinary English words,
  returns **0 findings** - no credential shapes, no client names, no internal hosts. Stripe and
  Chase appear once each, generically.

So the defect is governance, not exposure: it is public by accident rather than by decision. That
is a one-line answer from Phoenix (HUMAN_ACTION 4), and per the correction it does **not** hold the
release - the release is DRAFT because approval is a human act, which is a separate gate.

Precision took two rounds, both worth recording:

- A denylist built mechanically from folder names produced **178 "client names"**, every one an
  ordinary English word. Generic single words are now reported and skipped by default and never
  silently dropped - a real client can be called Enable, and a silent drop is a false negative,
  which is worse. Release mode fails closed unless the operator widens the list or acknowledges
  the gap.
- Bare prefixes matched, so the `security_check` skill tripped the scanner simply for documenting
  the shapes it looks for. Patterns now require a plausible key body.

**178 -> 1, and the one that remains is real.** Both client names that are ordinary English words
were then checked deliberately in a second pass: every hit was ordinary English usage.

Findings carry a fingerprint for high-entropy secrets and **no hash at all** for client names and
internal URLs, which are enumerable - a hash of a client name lets anyone with a candidate list
confirm a guess.

**Bounded claim.** Documented in the module, not implied away: a secret assembled across source
lines is not detected; encodings beyond UTF-8/UTF-16/base64 are not decoded; internal hosts are a
known-pattern list plus private address space, not a proof; and the scan covers the pinned tree,
which says nothing about a "Use this template" copy of a mutable branch.

## 6. The delivery path nobody had noticed

`README.md` promises you can "re-pull improvements from the template brain on demand". Nothing
implemented that. GitHub templates do not sync, so a generated workspace was **frozen at birth**
with no record of what it contained.

Worse for the contract: "Use this template" copies mutable `main`, which is precisely what founder
ruling D3 forbids. `aios adopt` is the way back - it proves a workspace matches an approved
release byte for byte, then pins it - and `start` says `UNPINNED` until it does.

## 10. Reusable lessons

1. **Presence is not enforcement.** A file that exists, a check that is green and a rule that
   matches nobody can all be true at once. Every "is X configured?" check should assert the
   *effect*, not the artifact. Canonicalized as the CODEOWNERS binding + placeholder checks;
   propagated by the 32-repo sweep, which found 5 more decorative gates.
2. **A red check that is always red is not a check.** `ai_review` failed on every PR for three
   months for a configuration reason and nobody read it. Distinguish "not configured" from
   "broken" in the status itself.
3. **A scanner's precision is a safety property.** 178 false positives would have got the scan
   switched off, and the one real finding with it.
4. **Never silently narrow a check.** Truncating at 4MB, skipping a generic denylist term, or
   suppressing a whole line is fine only if it is *reported*; otherwise the claim quietly becomes
   smaller than it sounds while reading the same.
5. **Test the recovery path against a real kill.** The exception path and the `kill -9` path are
   different code. The journal had to record what an upgrade *intended* to add, because after a
   hard kill the install record still describes the old release.
6. **An evidence location is part of the threat model.** The mandated evidence path here is a
   public template repo. Now contract rule 11 for every lane.
7. **"Works on my machine" has a specific shape worth naming.** The end-to-end run passed on
   macOS and failed eight assertions on the Linux runner, all from one cause: macOS's system
   Python redirects bytecode to a central `pycache_prefix`, so `__pycache__` never appeared
   beside the source here. On a normal Python it does, `git add -A` sweeps it in, it ships in
   the package, and it then collides with the bytecode the client's own workspace generates -
   so the client could never upgrade. A local pass on a packaging claim is not evidence; the
   clean runner is. Fixed in three layers (gitignore, package spec, a deterministic test).
8. **A test fixture carrying a realistic secret will trip your own secret scanner.** The e2e
   wrote a contiguous fake key and the PR floor blocked the PR, correctly. The floor's own
   source solves this by assembling literals from fragments; the fixtures now do too.
