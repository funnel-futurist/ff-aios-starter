## Standing check: nothing written into another repository
`SubmoduleSweep` and `SubmoduleSweepMoves` (in `tests/aios/test_adopt_existing_3_1.py`, part of the full suite) are the check for this whole class, from review round 58 on. Later rounds run them; they don't add per-path tests.
- **By operation, not by path.** Each operation that writes runs once on a copy with every write call recorded: file opens for writing, replace, rename, link, remove, chmod, folder creation and removal. That gives every folder it touches, including temporary files and same-byte rewrites that leave no difference at the end. The operations are install, adopt, `adopt --existing`, an adoption's upgrade, an upgrade with the 2.x to 3.0 folder move, that upgrade's dry run (which probes for hard links), an upgrade's rollback, a folder move's rollback, an adoption's undo, and clearing a dead lock.
- **Recovery too.** Each operation that keeps a journal is also killed partway through the real command line, and its recovery is swept the same way: a killed adoption, a killed upgrade, a killed folder move, a killed rollback of either, and a killed undo.
- **Two kinds of other repository.** In a fresh copy for each folder, that folder becomes a submodule (its tracked files untracked and left on disk, a gitlink committed), and then, separately, a nested repository with its own `.git`. Each time the operation must refuse and name the folder, leave every file, every folder and git's view byte-identical, and not even attempt a write inside that folder: the refused run is recorded too, so a lock made and removed before the refusal still counts. The one change allowed is a killed run's dead lock outside that folder, which recovery reclaims by design.
- **A new operation can't skip it.** A registry test fails when a public function in the installer is neither swept nor listed as read-only.
- **It discriminates.** At `934c990`, before round 58's fixes, the first version failed 23 folder cases. At `341b426`, before round 59's fixes, the second version failed 44 recovery cases. At `75753b0`, before round 60's fix, this version fails 10 cases, each with `.aios` as the other repository, where the workspace lock was written before any check ran.

**And statically: the write-site inventory** (`tests/aios/test_write_sites.py`, from round 61, at Chat Zero's direction). It reads the package's source and lists every call that writes to disk: 147 calls in 56 functions. Each function is classified after review ("own", "callers", "primitive" or "allowlist", each with its reason), and the test fails on a write the table doesn't list, a changed count, or a check taken out from before a write. Its controls remove the rollback's check, add an unlisted write, and add a git write through each wrapper; each makes it fail.

**And at runtime: the audit backstop** (`tests/aios/audit_writes.py`, from round 63, at Chat Zero's direction). Python's audit hooks (PEP 578) record every write the interpreter actually makes, and every git it runs, whatever the source looks like. They run in the sweep and in every command-line process of the integration test (`audit_site/sitecustomize.py`, checked by `audit_check.py`). Every write must stay in the test's folder or the system's temporary folder; nothing may go into a `.git` folder but the installer's guard, or into the Starter's source repository; every git command must only read. A write the static scanner can't read (an `open` and a `remove` reached through `getattr`) is caught at runtime, and a crafted log fails each check.

- **GitHub's own `tests` check, rounds 62 to 68 (heads `f9e9b9f` to `0b933ab`).** It failed on all seven heads while every local run, every chain and both reviewers passed. It was found only at the release step. The integration test's runtime audit caught a write into the Starter's source repository: `scripts/aios/aioslib/__pycache__/*.pyc`, written by Python's import system during `release build`. A real first install runs the CLI from a Starter clone the same way. No Mac run showed it: Apple's `/usr/bin/python3` caches bytecode under `$HOME/Library/Caches/com.apple.python` (the test's own home under its scrubbed environment), while Ubuntu's Python 3.12 caches beside the source.
  - **The fix is in the product:** `aios.py` sets `sys.dont_write_bytecode` before importing anything of the package. The integration test is unchanged, so GitHub's run proves the fix.
  - **Shown both ways:** `NoBytecodeBesideThePackage` fails on `0b933ab`. Two scratch clones at `0b933ab`, with an audit hook that behaves like Linux's Python, fail the source-repository line without the fix and pass it with the fix.
  - **Since then the chain ends by reading GitHub's check runs on the exact head,** and fails unless `tests` and `governance` succeed.
